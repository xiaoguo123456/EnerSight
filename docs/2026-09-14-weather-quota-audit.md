# 测试环境气象日额度排查

排查日期：2026-09-14，北京时间。只读检查容器、配置、缓存和数据库，并执行一次最小单点气象请求；未触发全目录重算或修改线上配置。

## 已确认的事实

- 测试服务器直连 Open-Meteo 返回 HTTP 429，原因是 `Daily API request limit exceeded. Please try again tomorrow.`，明确属于日额度耗尽。
- 官方限流实现按 Unix 时间的 UTC 日边界清零，对应北京时间 08:00。因此北京时间 00:00 后仍可能处于上一轮计费日，不能把零点后不足一小时等同于一个全新的额度周期。线上重置行为仍以上游实际运行配置为准。
- 当前容器启动时间为北京时间 01:08:17；`enable_scheduler=False`，启动日志只列出 `map_prepare`。全目录定时任务没有启用。地图原生栅格预处理与预测查询 API 为不同链路。
- `/opt/enersight-test/data` 挂载到 `/app/data`，常规容器部署不会清空这些文件。但进程内缓存、预算和退避状态会随重启丢失。
- 目录有 18,764 条运行中记录，经现有资格筛选后为 8,215 座可参与估算场站，对应 2,747 个唯一气象坐标。按当前九变量、八天请求，一轮全冷缓存拉取约消耗 2,747 个坐标调用额度，另有元数据和单站请求开销。批量合并只减少 HTTP 请求数。
- 9 月 13 日的 15 分钟天气索引保存 1,700 个坐标文件；9 月 14 日没有新的天气索引。14 日汇总保留旧预测，覆盖 4,120 座，状态为 partial，提示本轮未取得有效数据。

## 代码中的消耗因素

1. `fleet_prediction.ensure` 由全目录查询触发后台检查；不是只有定时任务或部署才能触发计算。
2. 气象缓存索引和网格文件按模型、北京时间目标日期隔离。换日后不会直接复用昨日索引，即使其七天预报仍覆盖新一天。这会产生额外回源需求。
3. 索引在分辨率不为 15 分钟、起报批次变化或超过 12 小时时失效。小时数据迁移到 15 分钟因此有一次重新取数需求；后续普通部署并非每次必然全量重取。
4. 当前共享预算只有每分钟 480 个额度单位，没有小时、每日持久化账本。分钟速率合规无法保证日总量充足。假设每轮均需全量更新，四轮约 10,988 个坐标额度，已经超过免费日额度，尚未包括其他入口。
5. 限流缺少 Retry-After 时默认退避 60 秒，没有按日限额区分恢复时间。日志中部分全目录批次在本地预算层直接抛出 UpstreamRateLimited，并没有发出请求；不能把这些错误日志条数算作实际消耗。

## 结论与证据边界

日额度耗尽已确认；北京时间换日未重置上游额度是时间上的关键误解。全目录拉取、分辨率迁移和缓存换日隔离均有较大的额度影响，普通部署不会清空磁盘缓存。现有日志与缓存不足以还原所有成功请求的计费总量，因此不能断言是哪一次改动独自耗尽了一万次额度。

优先改进：按模型、起报批次、坐标、字段及实际时间覆盖复用气象数据，跨日裁剪已有序列；将计算版本与原始气象缓存解耦；持久化小时／每日预算并为前台预留额度；记录请求入口、坐标权重、缓存命中和限流类别；识别日限额后延长冷却并保留旧快照。以上是排查建议，本次未实施。
