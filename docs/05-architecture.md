> EnerSight AI 新能源气象遥感分析平台 · 文档包 V1.0
>
> 端演进路径：**微信小程序（V1）→ App（V2）**


## 一、选型结论


| 层 | 选型 | 说明 |
| --- | --- | --- |
| 小程序框架 | Taro 4 | 基于 Vite，编译到微信小程序 |
| UI 框架 | React 18 + TypeScript | 严格模式 |
| 状态管理 | Zustand | 纯 TS、无平台依赖，可下沉到 core 层 |
| 样式 | Sass + CSS 变量 | 设计 token 用 CSS 变量，跨端一致 |
| 图表 | Canvas 2D 自绘或 F2 | 见 6.2 |
| 地图 | 微信 `<map>` + 服务端渲染贴图 | 见第六章，架构核心 |
| 包管理 | pnpm workspace | monorepo |
| BFF | Python 3.12 + FastAPI | 科学计算生态，见 1.2 |
| 类型同步 | FastAPI OpenAPI → `openapi-typescript` | 生成 `core/types` |


### 1.1 前端选型依据

React 生态成熟、类型体系完善；组件全部自研（37 个，见 03），
不依赖跨端 UI 库，因此跨端框架最大的坑（组件库不兼容）在本项目不存在。

> 若团队主力是 Vue，改用 uni-app + Vue 3 同样成立，
> 本文档除框架名外的所有架构决策均不受影响。


### 1.2 后端为什么是 Python

**这个后端的本质是数据处理，不是 CRUD 服务。**

气象网格插值、卫星影像处理、太阳几何、光伏建模、色阶渲染 ——
每一项在 Python 里都有成熟的行业标准库，用 Node 或 Go 都要自己造轮子。

| 需求 | 库 | 替代方案的代价 |
| --- | --- | --- |
| 太阳位置、晴空辐射、电池温度、GTI | `pvlib` | 手写简化公式，精度低且难验证 |
| 云团位移估计（光流） | `opencv-python` | 自己实现光流算法 |
| 网格插值 | `scipy.interpolate` | 自己实现双线性/克里金 |
| 卫星影像读写 | `rasterio` | 手工解析 GeoTIFF |
| 气象格式 GRIB / NetCDF | `xarray` + `cfgrib` | 几乎无可用实现 |
| 色阶渲染 | `numpy` + `Pillow` | 可行，但插值仍要自己写 |

其中 **`pvlib` 近乎决定性**：它是 NREL 支持的光伏建模事实标准库，
[07 文档](./07-metrics.md) 中手写的太阳赤纬、日出日落、晴空辐射、
电池温度模型，在 `pvlib` 里都有精度更高的现成实现（见 07 附录 A）。


### 1.3 类型如何同步

FastAPI 从 Pydantic 模型自动产出 OpenAPI schema：

```
server/  Pydantic 模型
   ↓  自动生成
      openapi.json
   ↓  openapi-typescript
core/types/  TypeScript 类型
```

纳入 CI：schema 变更未同步生成则构建失败，避免前后端类型漂移。


### 1.4 代价

| 代价 | 说明 |
| --- | --- |
| CPU 密集任务仍会阻塞 | numpy / OpenCV 计算释放 GIL，但在 async 路由里同步调用照样卡住该 worker，见 6.6 |
| 镜像体积 | 比 Go 大，依赖管理用 `uv` 控制 |
| 性能余量最小 | 三种语言中最小，但 6.5 测算仅 0.58 核，余量足够 |
| 类型不能直接共享 | 需 codegen 一层，由 1.3 的 CI 约束兜住 |

## 二、跨端策略


### 2.1 一个必须先说清楚的判断

**不要指望一套代码直接编译出 App。**

Taro RN、uni-app nvue 在重图表、重地图场景都会掉链子。
把 App 押在「编译一下就有了」上，是本项目最大的隐性风险。


### 2.2 真正能兑现的复用：逻辑层

```
复用      packages/core     纯 TS，零 UI 依赖
                            类型定义（codegen）、API client、格式化
                            ↑ 小程序与 App 100% 共用

不复用    UI 层             各端各写
                            小程序用 Taro，App 用 RN 或 Flutter
```

> **指标计算不在 core 层。** [06 契约](./06-api-contract.md) 已定为
> 服务端算好后返回（`EnergyIndex` 直接给出 score / level / factors），
> 端上不需要任何指标计算实现。这也是后端可以自由选语言的前提。

core 层承载的是「与后端语言无关、且两端必须一致」的部分：
接口调用约定、错误处理、单位进位与千分位规则。


### 2.3 演进路径

| 阶段 | 端 | 做法 |
| --- | --- | --- |
| V1 | 微信小程序 | Taro 编译，core 同步建立 |
| V2 | App | UI 用 RN 重写，直接依赖 core |
| 可选 | H5 | Taro 同源编译，成本最低 |

```
├── packages/
│   ├── ui/                 设计稿
│   ├── core/               ★ 跨端复用层（纯 TS）
│   │   ├── types/          数据模型，与 04 文档对应
│   │   ├── api/            API client，与 06 契约对应
│   │   ├── metrics/        指标计算，与 07 文档对应
│   │   └── format/         单位换算、千分位、时间格式化
│   ├── miniapp/            Taro 微信小程序
│   │   ├── src/pages/      6 个页面
│   │   ├── src/components/ 37 个组件，与 03 文档对应
│   │   ├── src/store/      Zustand
│   │   └── src/styles/     设计 token，与 02 文档对应
│   └── server/             BFF（Python + FastAPI）
│       ├── app/routers/    对外接口，与 06 契约对应
│       ├── app/schemas/    Pydantic 模型 → OpenAPI → core/types
│       ├── app/providers/  Open-Meteo / Himawari / 腾讯位置服务 适配
│       ├── app/metrics/    ★ 指标计算，与 07 文档对应（pvlib）
│       ├── app/render/     ★ 图层图片渲染
│       ├── app/satellite/  ★ 云图处理与光流位移估计（OpenCV）
│       ├── app/ai/         AI 编排，与 08 文档对应
│       └── app/jobs/       定时任务
├── pnpm-workspace.yaml
└── Makefile                跨语言任务入口（codegen、lint、test）
```

依赖方向严格单向：

```
miniapp ──→ core ──→ 不依赖任何端

server  ──→ 不依赖 core（语言不同）
        ──→ 通过 OpenAPI 单向产出 core/types
```

前后端的唯一契约是 OpenAPI schema，不是共享代码。

## 四、packages/core 职责


| 模块 | 内容 | 来源 | 对应文档 |
| --- | --- | --- | --- |
| `types/` | Station、Weather、Layer、Alert、AIReport 等模型 | **codegen 生成，不手写** | 04、06 |
| `api/` | 请求封装、错误处理、重试；平台差异通过注入 adapter 隔离 | 手写 | [06](./06-api-contract.md) |
| `format/` | kW/MW 与 kWh/GWh 进位、千分位、经纬度、时区 | 手写 | 02、04 |

`types/` 目录纳入版本控制但标记为生成产物，禁止手工修改。


**平台差异隔离**：core 不直接调用 `Taro.request` 或 `fetch`，
由各端注入一个 `HttpAdapter`：

```ts
// core
export interface HttpAdapter {
  request<T>(opts: RequestOptions): Promise<T>
}

// miniapp 注入 Taro.request
// app 注入 fetch
// server 注入 undici
```

**指标计算不放 core。** 06 契约已定为服务端算好返回，端上没有计算需求；
放在 core 只会产生死代码，并把后端锁死在 TypeScript 上。

## 五、BFF 是必需的


不是可选项，四个硬理由：

| # | 理由 |
| --- | --- |
| 1 | 小程序 `request` 合法域名必须 HTTPS + ICP 备案，且有数量上限。直连 Open-Meteo / Himawari 走不通 |
| 2 | 图层需要服务端渲染成图片（见第六章） |
| 3 | AI 的 API Key 不能下发到前端 |
| 4 | 环比要存昨日数据；Himawari 10 分钟一帧应全用户共享缓存，不能每端各拉一次 |


### 基础设施选型

| | 选型 | 理由 | 升级路径 |
| --- | --- | --- | --- |
| 数据库 | SQLAlchemy 2.0 async + Alembic；本地 SQLite，线上 PostgreSQL | 本地零依赖起步，Alembic 管迁移 | 换 `DATABASE_URL` 即可，迁移用 batch 模式兼容两端 |
| 缓存 | 进程内 TTL cache，接口抽象 | 单实例够用 | 水平扩容时换 Redis，业务代码不动 |
| 调度 | APScheduler 进程内 | V1 不需要独立 worker | 任务量大时拆 worker |

时间字段一律存 **naive UTC**，出口再按站点时区格式化 —— SQLite 与 PostgreSQL
对 timezone-aware 的处理不一致，统一成 naive UTC 最省事。

非 debug 模式下带着开发默认值（JWT 密钥、SQLite）启动会被拒绝，见 `main.py`。


### BFF 职责

```
对外：一个域名，收敛所有第三方依赖

├── 数据聚合    Open-Meteo 多字段合并为一次响应
├── 缓存        网格级缓存，相邻站点命中同一份
├── 指标计算    pvlib + numpy，见 07 文档
├── 图层渲染    气象网格 / 卫星影像 → PNG（无状态模块，见 6.6）
├── 云图处理    OpenCV 光流位移估计，见 07 §4.1
├── AI 编排     见 08 文档
└── 定时任务    预渲染图层、预生成报告、扫描预警、拉取云图
```

渲染与 AI 都放在定时任务里跑，不进请求路径 —— 这是 BFF 能用单体扛住的前提。


### 定时任务的错峰与并发

| 任务 | 触发 | 说明 |
| --- | --- | --- |
| `scan_alerts` | 每小时 5/20/35/50 分 | 卫星 10 分钟一帧，短临外推要跟得上 |
| `accumulate_generation` | 每小时 10 分 | 错开整点的气象更新，也错开 scan_alerts |
| `archive_cloud` | 每小时 2/12/…/52 分 | JMA 帧延迟约 10 分钟 |
| `backfill_address` | 每小时 20 分 | 逆地理编码，每轮 100 条省配额 |

`accumulate_generation` 与 `scan_alerts` 都要遍历全部站点。气象数据本就共享同一份
批次缓存，撞在同一分钟不会多打上游，但会把 CPU 峰值堆到一起 —— 所以错开一格。

**遍历站点的任务一律分批取站点**，用 `db.pages` / `db.id_pages` 做 keyset 翻页 ——
全表一次 `.all()` 在几万座站上是定时炸弹，offset 分页在深页又会退化成全表扫描。

并发口径按「算与写能不能分开」分成两种，不要套用错：

| 任务 | 口径 | 为什么 |
| --- | --- | --- |
| `accumulate_generation` | **算并发、写串行**（`accumulate_concurrency`，默认 8） | 算完只产出一个数据类，写入集中在末尾。`AsyncSession` 不能被多个任务同时用，所以只有算的阶段进 `gather`。查询与提交按 `accumulate_batch_size` 分批 —— 攒到最后一次 `commit`，跑到一半出错前面全白跑 |
| `generate_reports` | **一任务一会话**（`reports_concurrency`，还会被 `db_pool_size` 夹一次） | `generate_and_store` 从取数、算指数到写库全程同一个会话，算与写分不开，且它自己提交。只能每个任务开自己的会话，因此并发上限受连接预算约束（线上 `db_pool_size` + `db_max_overflow` 一共 3 个），翻页用 `id_pages` 每页取完就放掉连接 |
| `scan_alerts` | **串行**，只分批取站点 | `scan_station` 自带 per-station 锁并各自提交，跨站点本就独立；但整轮共用一个会话。每 15 分钟一轮，没必要为并发再引入一套会话管理 |

`scan_alerts` 除个人站点外还要回扫「仍有生效预警、但已不在站点表里的公开电站」——
首页顺手扫过它们才会留下预警，不接着扫就永远解除不掉。用 `NOT EXISTS` 子查询挑出来，
而不是把全部站点 id 拉进内存做差集。

**全目录汇总按坐标限速。** Open-Meteo 免费层的 600 次/分钟是**按坐标计**的
（2026-09-13 实测：一分钟内推到第 600 个坐标即 429，与分成几次请求无关），
限额还按 IP 算、与站点预报和元数据共用。所以 `fleet_coords_per_request`
（一次请求带几个坐标）只省 HTTP 往返、不省额度，真正要控的是
`fleet_coords_per_minute`（默认 480，留两成余量），由 `fleet_prediction.Pacer` 执行。
1° 的 741 格限速后约 93 秒；每个模型每天只拉一轮（见 04 §二），可接受。

不限速的后果不是假设：改之前 741 个坐标以约 1000 坐标/分钟推出去，冷缓存时必然
在第 600 个坐标处被 429，靠 12 小时天气缓存 + 30 分钟重试才慢慢补齐，
全目录汇总因此长期停在 `partial`。

**上游拉取一律带退避重试、限并发。** `upstream_retries` 3 次、`upstream_backoff_seconds`
线性退避，只重试传输错误与 5xx；429（配额）与 400（坐标越界）立即抛出 —— 对 429
重试尤其有害，额度按天算。连接池上限 `upstream_max_connections`，避免并发算站点时
连接数随站点数线性膨胀。

预警列表及当前预警在查询场站后立即结束只读事务，再拉取气象与卫星数据；
等待上游期间不得占用数据库连接。气象源返回 429 后进入共享冷却期，
后续回源立即返回 `UPSTREAM_RATE_LIMITED`（503），已命中的有效缓存仍可使用。
客户端不自动重试配额错误，避免冷却排队与请求重试共同耗尽连接池。


### 缓存策略

| 数据 | TTL | 缓存键 |
| --- | --- | --- |
| 站点预报（实时天气、指数、趋势、预测共用同一份 15 分钟 Forecast） | 每坐标每天最多回源 4 次（按当地时段，跨时段批次未变不重拉） | 模型 + 精确经纬度 |
| 全目录预测气象 | 每模型每北京日一轮（08:00 起），缺失坐标限轮续拉 | 模型 + 日期 + 格心坐标（落盘） |
| 图层网格块 | 1 小时 | 模型 + 4° 块 |
| 卫星云图帧 | 10 分钟 | 全局 + 时间戳 |
| 图层渲染图 | 与数据源同步 | 图层 + bbox + zoom |
| 环境指数 | 随站点预报缓存，不单独缓存（算一次约 50 ms） | — |
| AI 一句话结论 | 1 小时 | 0.25° 网格（见 08） |
| AI 完整报告 | 1 天 | 站点 ID + 日期 |

按网格而非按站点缓存是成本关键：气象数据本就是网格化的，
1000 个站点可能只落在 100 个网格里，缓存命中率相差一个数量级。

**站点预报按回源时段与起报批次限次。** 上游 6 小时才出一批，而定时任务 15 分钟扫一轮：
按 10 分钟时间片缓存会让每个网格每天回源 96 次、其中 92 次拿到完全相同的数据。
现在每个坐标每天最多回源 4 次：时段内不追新批次，进入新时段而批次没变继续复用，
跨当地日才必定刷新；元数据缺失也不会退化成每 10 分钟一次。全目录每个模型每天只拉一轮。
口径与计费见 [04 §二「字段预算与拉取节奏」](./04-data-specification.md)。

## 六、地图图层方案（架构核心）


### 6.1 问题

设计稿要求 5 个自定义数据图层 + 风场流线动画 + 色阶图例。

微信小程序的 `<map>` 是**原生组件**，能力与 MapLibre 这类 Web 地图库差距很大：
提供 marker / polyline / polygon / circle / ground-overlay / 个性化样式，
**没有自定义瓦片图层与 WebGL 渲染管线**。

设计稿里的白色流线粒子动画，在小程序原生 map 上做不出来。


### 6.2 方案：服务端渲染，客户端贴图

```
服务端

  Open-Meteo 网格 / Himawari 影像
        ↓  按 bbox + zoom 渲染色阶、流线
      PNG
        ↓
客户端

  <map> + ground-overlay 贴图
        + marker（站点）
        + cover-view（图例、控件）
```


代价与收益：

| | |
| --- | --- |
| 代价 | 需要服务端渲染能力；风场动画降级为多帧轮播；缩放时有重取延迟 |
| 收益 | 小程序 / App / H5 三端表现完全一致，不赌任何一端的地图能力；客户端逻辑极简 |


### 6.3 各图层落地方式

| 图层 | 落地 |
| --- | --- |
| 云图 | Himawari 影像裁剪 → PNG → ground-overlay |
| 温度 | 网格插值 → 色阶填充 PNG |
| 辐射 | 网格插值 → 色阶填充 PNG |
| 风场 | 服务端预渲染 8–12 帧流线 PNG，客户端轮播 |
| 站点 | 原生 marker，不走贴图 |


### 6.4 图片切分方式：量化块，不是 XYZ 瓦片

`ground-overlay` 本身就是「把一张图贴到一个矩形范围」，
没必要实现完整的 XYZ 瓦片协议。

```
把覆盖区域按 4°×4° 切成固定块，每块一张 512×512 图
按 zoom 分粗 / 中 / 细三档
bbox 对齐到块边界 → 相邻用户请求命中同一张图 → CDN 可缓存
```

对比：

| | 量化块 | XYZ 瓦片 |
| --- | --- | --- |
| 同屏图片数 | 1 – 4 张 | 15 – 20 张 |
| 客户端管理 | 简单 | 需随视窗增删几十个 overlay |
| 渲染量 | 更低（见 6.5） | 更高 |
| 通用性 | 自定义协议 | 标准，工具链成熟 |

V1 用量化块。规模上来后再切 XYZ 瓦片，服务端接口形态不变。


### 6.5 容量测算：服务器撑不撑得住


**先说结论：撑得住，而且很轻松。瓶颈不在 CPU，在带宽。**


#### 关键认知：渲染负载与 DAU 无关

图层是**全局共享**的 —— 同一时刻同一区域的辐射图，
一万个用户看到的是同一张。所以渲染量由「数据更新周期 × 覆盖区域块数」决定，
不是「QPS × 渲染耗时」。用户翻倍，渲染量不变，只有带宽翻倍。


#### 渲染上限锁定 zoom 8

这不是为了省资源，是源数据分辨率决定的。
气象网格 0.25°，往上放大没有任何新信息：

| zoom | 单瓦片跨度 | 含 0.25° 格点数 |
| --- | --- | --- |
| 6 | 5.625° | 22.5 |
| 8 | 1.406° | 5.6 |
| 10 | 0.352° | 1.4 |
| 12 | 0.088° | 0.35 |

zoom 10 以上一张图里连 1.5 个格点都不到，纯粹在插值。
**渲染到 zoom 8，客户端放大时直接拉伸**，视觉上没有损失。

zoom 12 全中国是 371,175 张瓦片，zoom 8 只有 1,518 张 —— 差 244 倍。
这条约束是整个方案成立的关键。


#### 渲染量（按 XYZ 瓦片、全中国全量预渲染的最坏情况）

zoom 3–8 覆盖全中国共 **2,096 张**。

| 图层 | 帧数 | 更新周期 | 张/秒 |
| --- | --- | --- | --- |
| 温度 | 1 | 1 小时 | 0.58 |
| 辐射 | 1 | 1 小时 | 0.58 |
| 云图 | 1 | 10 分钟 | 3.49 |
| 风场 | 12 | 1 小时 | 6.99 |
| **合计** | | | **11.6 张/秒** |

| 单张渲染耗时 | 所需 CPU |
| --- | --- |
| 20 ms | 0.23 核 |
| 50 ms | 0.58 核 |
| 100 ms | 1.16 核 |

**一台 2 核小机器绰绰有余。** 改用 6.4 的量化块方案后降到约 2.4 张/秒，更省。

而且这是「全中国全量预渲染」的上界。实际用**按需渲染 + CDN 回源**：
只有真被用户看到的块才渲染，V1 阶段实际量远低于此。


#### 真正的瓶颈：风场动画的带宽

| 场景 | 静态图层 | 风场 12 帧 |
| --- | --- | --- |
| 1,000 DAU × 3 次/天 | 34 GB/月 | 412 GB/月 |
| 10,000 DAU × 3 次/天 | 343 GB/月 | 4,120 GB/月 |

静态图层的量可以忽略。风场动画一开，带宽翻 12 倍。

应对（按优先级）：

1. 风场动画只在 zoom ≤ 6 提供（块数少一个数量级）
2. 帧数从 12 降到 6–8
3. 用 WebP 替代 PNG，体积再降约 30%
4. V1 可先降级为**静态风羽图**，动画留到 V2

> 第 4 条是最省的选择。设计稿的流线动画很好看，但它是全产品带宽成本的主要来源，
> 值得在 V1 阶段单独做一次成本/体验权衡。


#### 存储

2,096 张 × 4 图层 × 20 KB ≈ **170 MB** 常驻，可忽略。


#### 结论

| 项 | 结论 |
| --- | --- |
| CPU | 2 核足够，不是瓶颈 |
| 存储 | 170 MB，可忽略 |
| 带宽 | 静态图层可忽略；**风场动画是唯一需要控制的成本项** |
| 扩展性 | 渲染量与 DAU 无关，用户增长只影响 CDN 带宽 |

前提是三条都做到：渲染上限 zoom 8、按需渲染 + CDN 缓存、风场帧数受控。
任何一条破了，量级都会失控。


### 6.6 要不要做独立的地图服务


「地图服务」有三层含义，结论各不相同：

| 层 | 是什么 | 结论 |
| --- | --- | --- |
| 底图 | 地理底图瓦片 | **没得选** —— 小程序底图由腾讯地图内置 |
| 地图 API | 逆地理编码、地点搜索、坐标转换 | **买**，不自建 |
| 数据图层渲染 | 气象 / 卫星 → PNG | **自建，但 V1 不拆成独立服务** |


#### 底图：小程序端没有选择

小程序 `<map>` 的底图由腾讯地图提供，只能通过腾讯位置服务后台配置个性化样式，
**不能指向自己的瓦片服务器**。所以「自建底图瓦片服务」这个选项在小程序端不存在。

V2 做 App / H5 时才有选择空间（MapLibre + 自建或第三方瓦片），
但那时的判断依据是届时的规模与成本，现在不需要为它做设计。


#### 地图 API：买

以下能力自建不划算，用腾讯位置服务（与小程序 map 同源）：

- 逆地理编码 —— 站点 `address` 自动填充（见 04 文档）
- 城市 / 地点搜索 —— 地图页搜索框
- 坐标系转换

> ⚠️ **坐标系是个必须提前定死的坑。**
> Open-Meteo 与 Himawari 用 **WGS84**，腾讯地图用 **GCJ-02**，
> 两者在境内有几十到几百米偏移。站点经纬度、图层 bbox、marker 位置
> 如果混用坐标系，会出现「站点标记和云图错位」这类难查的 bug。
>
> 约定：**存储与计算一律用 WGS84，仅在传给 map 组件前转 GCJ-02。**
> 这条要写进 06 接口契约，每个含经纬度的字段都标注坐标系。


#### 图层渲染：V1 不拆

理由很直接：6.5 算过总量 **0.58 核**，为这个量拆微服务是过度工程。
多一个服务就是多一套部署、监控、CI 和排障成本，而现在连真实负载数据都还没有。


但有一个真实问题必须处理：

> **CPU 密集任务不能跑在 async 请求路径里。**
> FastAPI 的 async 路由跑在事件循环上，同步的 numpy / OpenCV 调用会卡住该 worker，
> 拖慢所有 API —— 包括跟地图无关的接口。
>
> numpy 与 OpenCV 在计算时会释放 GIL，所以**多线程是有效的**，
> 这与纯 Python 计算不同。但前提是不能在事件循环里直接同步调用。

> 补充：这不是 Python 独有的问题。Node 也一样 ——
> 区别只在 Node 用 `worker_threads`、Python 用线程池或独立 worker，复杂度相当。
> 选语言时不必把这条算作某一方的缺点。

两条应对，都不需要拆服务：

**① 把渲染移出请求路径（主要手段）**

```
定时任务预渲染热点区域  →  写入对象存储 / CDN

用户请求  →  永远命中缓存

冷区域    →  按需渲染兜底
```

渲染跑在 `jobs/` 里，天然与 API 路径隔离。

**② 线程池执行器（兜底手段）**

按需渲染那部分丢进 executor，不阻塞事件循环：

```python
await loop.run_in_executor(render_pool, render_tile, layer, bbox, zoom, t)
```

`render_pool` 用 `ThreadPoolExecutor`（numpy / OpenCV 释放 GIL，线程有效），
2–4 个线程足够覆盖 6.5 的测算量。

纯 Python 的计算才需要 `ProcessPoolExecutor`，本项目的热点都在 C 扩展里，不需要。


#### 按「随时可拆」的方式写

`server/app/render/` 保持**无状态**，不依赖 BFF 的数据库与会话：

```python
# 渲染入口是一个纯函数
def render(layer: LayerType, bbox: BBox, zoom: int, t: datetime) -> bytes: ...
```

将来要拆，就是把这个目录搬到新仓库、把函数调用换成 HTTP 调用，
业务代码零改动。


#### 拆分触发条件

不写「以后再说」，写明什么时候必须拆：

| 触发条件 | 含义 |
| --- | --- |
| 渲染 CPU 持续 > 1 核 | 覆盖区域或帧数比测算扩大 2 倍以上 |
| 一轮预渲染跑不完 | 渲染耗时 > 数据更新周期，开始堆积 |
| 需要独立扩缩容 | 如扩展到海外，渲染量与 API 量脱钩 |
| 渲染故障影响 API | 说明隔离没做好 —— 先修隔离，不是急着拆 |


#### 为什么不用现成的气象图层服务

Windy、Tomorrow.io 这类提供现成气象瓦片，但四条都不满足：

| 问题 | 说明 |
| --- | --- |
| 样式不可定制 | 对不上 04 定义的 0–1000 W/m² 六档色带 |
| 数据源不受控 | 图层数值可能与站点卡片、AI 报告对不上 |
| 成本随 DAU 增长 | 按调用量计费；自建是固定成本 |
| 境内可达性 | 与 08 文档的 AI 选型是同一类问题 |

自建渲染已经算过是 0.58 核，没有理由外包。

| # | 事项 | 处理 |
| --- | --- | --- |
| 10 | 存在 `addVisualLayer` / `executeVisualLayerCommand`（腾讯位置服务的数据可视化图层，如热力图） | **不采用**：需在腾讯后台配置图层 ID 并上传数据，不适合高频更新的气象场。且已知 `addVisualLayer` 会被 `addGroundOverlay` 覆盖，需注意调用顺序 |

以下无法从文档确认，需在微信开发者工具与真机上实测：

| --- | --- | --- |

### 2026-09 地图栅格模块（当前实现，替代前文早期大图方案）

温度、风场、辐射由现有 FastAPI 内的 `render/map_raster.py`、`services/hres_layer.py`
与 `jobs/map_prepare.py` 提供，不新增容器。使用 Rasterio/GDAL 的 COG、窗口读取和重投影能力；
保留现有受控图层接口，不开放任意远端 URL 的通用切片端点。

- 数据：Open-Meteo 托管的 IFS HRES O1280 原生网格，约 9 km；非点 API 拼图。
- 覆盖：60–150°E、0–65°N（中国及周边），边界之外透明，不将边缘像素外推。
- 预处理：启动 10 秒后、之后每 10 分钟检查完整批次；优先当前时效，再准备未来两小时。
  温度/风取整点瞬时场，辐射取包含当前时刻的区间末标签。
- 成果：浮点 COG，含内部概览、NaN 缺测。保留 WGS84 计算坐标成果，另生成逐像素反变换的
  GCJ 显示成果。后者仅作显示用途，不作为标准 EPSG:4326 数据导出。像素中心与源网格节点对齐。
- 图片：256px Web Mercator XYZ，固定批次/时效/图层/坐标系/z/x/y 缓存。z3–5 提前生成；
  其他层级从本地 COG 按需生成，最高 z8。放大只改变展示密度，不提高模型实际分辨率。
- 小程序：根据 bbox 自动选层级，一屏最多 12 张覆盖图，适配 `addGroundOverlay`；
  模拟器用同一组墨卡托图片预览。HRES 不再限制 24° 视野，云图暂保留原有独立限制。
- 在线请求：不下载原始模型、不进行全国栅格转换；只有本地瓦片生成与少量数值采样。
  若当前成果未就绪，最多使用两小时前成果并标 `stale`，无可用成果时返回 `MAP_PREPARING`。
- 资源：同容器中后台和在线各一个工作进程；在线最多两个待执行任务。文件锁阻止多 API
  进程重复预处理，单帧工作进程也持锁；成对 COG 完整写入后才原子发布清单。
- 缓存：按有效时刻保留 48 小时的 COG 和 PNG；不是按起报日期误删仍有效的预报。
- 表达：温度固定色阶加 2℃ 等值边界，保留绝对数值图例；仅图片自身透明，不再双重降低透明度。

前端响应缓存仍按精确视野区分，风粒子使用独立 U/V 矢量而非从颜色反推风向。
HTTP Range 校验状态、字节长度及 Content-Range；预处理失败不会回退到粗点插值图。

#### 地图缩放与图层说明（2026-09-10 修订）

- 多级 XYZ 按实际视野选择，单次最多 12 张；模拟器手势或按钮缩放先撤下旧屏幕贴图，结束后重新查询视野再加载。兼容事件阶段位于顶层或 `detail`，不再依赖 `causedBy` 才更新；相同视野去重，避免贴图更新触发请求循环。
- 温度仅使用连续色带，不绘制等温线。图片路径增加 `smooth-v2` 样式目录，使旧缓存失效；原始 COG 和预处理成果仍可复用。
- 左上角只展示模型和北京时间时分，点击信息标记查看完整日期、分辨率、来源与覆盖范围；失败时点击重试。

- 真机防闪烁：原生地理覆盖层在拖动、缩放时保留，新批瓦片全部成功后再移除旧批；失败只清理未完成批次。图层切换及离开页面才完整清理。原生 `causedBy=update` 不触发重载，视野小于千分之一的浮点抖动被忽略。模拟器仍撤下固定屏幕预览，两端不能共用先清空的逻辑。此修复须上传新的小程序体验版才能在手机生效。
