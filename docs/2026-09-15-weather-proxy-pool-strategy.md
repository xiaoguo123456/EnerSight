## 一、建议结论

采用「按实际出口 IP 分组、按预算分配请求、按故障范围冷却」的轻量代理池。
先维护 **5～10 个经过验证的独立出口**，保留少量备用。用户访问先查天气缓存，
缓存未命中才申请预算、选择代理。后台自动发现、检测、补充和淘汰，页面不负责找代理。

重要依据：实测 A 出口的前 600 个单字段坐标成功、下一批收到分钟 429，同一分钟 B
出口的单坐标请求仍成功。另一个代理的地址与实际出口不同，不能按代理地址统计独立额度。
这只验证了两个出口在该时段的分钟限额表现，小时、日额度及其他代理仍需分别记录和验证。

## 二、分开管理代理节点与出口

| 对象 | 记录内容 | 用途 |
| --- | --- | --- |
| 代理节点 | 协议、地址、端口、来源、最近检测、成功率、耗时、连接失败次数 | 判断能否连通、选哪条连接 |
| 实际出口 | 观测到的公网 IPv4、验证时间、关联节点、各时间窗口用量、冷却截止时间 | 共享预算与限流状态 |
| 单次尝试 | 请求标识、节点、出口、成本、状态码、失败类型、耗时、是否重试 | 追溯配额与切换原因 |

同出口的多个节点、端口共享同一本额度账；一个节点恢复连接后必须重新核对出口。
出口变化时重新关联，但保留旧出口的计数和冷却，不能通过换端口或重启清零。
所有额度分组还必须包含上游身份范围：这里只适用于公开接口；今后 API key、CF 转发
需按各自身份规则处理，不能套用公网 IP 分组。

### 入池流程

1. 从官方列表取得候选，只接受公网 IP 字面量；拒绝内网、回环、凭据及异常 URL。
2. 使用 HTTPS CONNECT、验证目标证书，查询实际出口；首次入池用两次独立连接确认一致。
3. 获取一次小型模型元数据，验证目标服务可用；这次访问计入气象预算。
4. 成功后进入可用池，并与已有出口去重。相同出口最多保留两个节点作连接备用。
5. 出口查询失败、结果不一致或气象验证失败，留在候选区，不作为独立出口承接业务。

出口查询服务看到的 IP 只是观测证据，不等于读到了 Open-Meteo 连接日志。
如果代理按目标域名分配不同出口，这种办法无法完全识别；异常限流时重新验证，
不能承诺“每换一个地址就有一份新额度”。首期只接受稳定 IPv4 出口，动态出口暂不入池。

## 三、自动补充与淘汰

以下为建议初始参数，可根据测试数据调整。

| 项目 | 初始策略 |
| --- | --- |
| 可用出口目标 | 10 个，至少 5 个；不足 3 个时记录降级事件 |
| 候选上限 | 100 个，优先选择官方近期成功记录较好的节点 |
| 列表刷新 | 每 15 分钟增量更新，附少量随机延迟，保留已验证节点 |
| 低水位补充 | 可用出口少于 5 个时提前补充；两轮至少间隔 5 分钟 |
| 检测预算 | 每轮最多 20 个候选、检测并发 2；出口查询超时 4 秒 |
| 出口有效期 | 15 分钟；过期后后台复核，确认前暂停承担新请求 |
| 气象健康有效期 | 30 分钟；业务成功可续期，空闲节点到期才探测元数据 |
| 连续连接失败 | 依次冷却 1、2、4、8 分钟，最多 1 小时；冷却后单次探测 |
| 淘汰 | 连续失败 5 次或 24 小时没有成功，退出活跃池；失败历史保留 24 小时 |

免费列表再次收录已淘汰地址时，不立即重置它的失败历史。新候选需要完整验证。
一轮检测拿不到新节点时继续服务已有健康节点，不循环抓取整个列表。
列表直连失败，可通过已有健康节点取得同一 HTTPS 官方列表；全部失败则保留快照，
五分钟后再试。初次启动允许一天内的官方列表快照引导，但快照里的地址必须重新验证。

## 四、请求调度与预算

### 1. 先查缓存，再选出口

```text
天气缓存命中 → 返回现有有效数据
       未命中 → 合并相同天气请求 → 检查项目总预算
                                      ↓
                   选择健康、出口已验证、余额足够的节点
                                      ↓
                        原子预留出口预算与并发名额
                                      ↓
                           请求、记录结果、更新缓存
```

相同坐标、模型、预报参数的并发请求合并，缓存时效遵循既有数据规范。
代理节点不同不应导致重复拉取同一份天气。

### 2. 按计费单位记账

不能以 HTTP 次数代替成本。沿用 `request_cost` 对坐标数、变量数、天数的估算，
先覆盖当前单模型请求；增加多模型参数时先补齐成本规则。每次重试、元数据探测均计账。
网络超时也保守记账，因为请求可能已到达上游。600 个坐标的实测阈值仅对应此次单字段请求。

建议测试起步时：

- 项目合计仍保持现有 **480 单位/分钟**；本轮先验证可用性与隔离，不提高总吞吐。
- 每出口本地预算先设 **300 单位/分钟、2,000 单位/小时、5,000 单位/24 小时**。
  这是我们自设的保守阈值，不是上游承诺额度；免费出口还可能被其他人占用。
- 使用滑动窗口，不在整点一次性突发释放预算；计数与并发预留必须原子完成。
- 一批成本超过出口窗口上限时先拆批，不能等待几轮预算后仍一次发送整批。
- 请求优先分配给近期使用较少、余额充足的出口，再在其中优先选稳定且较快的节点。
  避免始终把全部流量压到最快的一个出口；一次请求只选择一个节点，不并发竞速拉相同数据。
- 全局并发最多 4，每出口最多 1。后台目录任务并发最多 2，优先让前台使用剩余名额。
  前台没有立即可用预算时及时降级，后台任务可排队等待。

所有调用方必须共用一个预算入口，避免 Provider、批量任务和代理池分别收费或漏记。
总预算控制项目负载，出口预算控制节点使用量，两层职责分开。

## 五、失败与冷却

| 结果 | 冷却范围 | 当前请求处理 |
| --- | --- | --- |
| 200 且业务数据有效 | 无 | 更新缓存、健康度与耗时 |
| 连接超时、断连 | 当前节点 | 剩余时间允许时换一个不同出口，最多再尝试一次 |
| 证书错误、200 HTML、异常重定向 | 当前节点隔离，重新验证 | 不接受响应内容；最多换一个已验证出口 |
| 上游 400 参数错误 | 不惩罚出口 | 返回对应业务错误，不换代理重试 |
| 明确的免费接口分钟 429 | 对应出口及其全部关联节点 | 停止该出口；符合总预算和重试上限时，可尝试另一个有余额的已验证出口 |
| 明确的小时或日 429 | 对应出口及其关联节点，较长冷却 | 当前请求不立即换出口重试，触发用量检查；其他未受限出口处理后续合规预算内的请求 |
| 来源或作用范围不明的 429 | 保守使用共享冷却 | 不依赖换 IP 推断已解除限制，记录原始原因供检查 |
| 上游 5xx | 记录上游故障，不判成额度不足 | 有限退避；短时间多个出口都失败时暂停该上游 |

`Retry-After` 支持秒数和 HTTP 日期，作为最早恢复时间；没有该头时，分钟冷却默认
60 秒，小时默认 3,600 秒，日默认 86,400 秒，未知默认共享冷却 60 秒。
这些是保守等待策略，不假设服务端一定在某个整点重置。冷却截止后只放一个探测请求，
成功才恢复，失败继续退避，不能一到时间就放出全部积压请求。

整个用户请求最多 **2 次实际天气访问、14 秒总时间**，包括排队、退避与换节点；
不因换了故障类型重新获得重试次数。禁止代理池两次重试再乘 Provider 三次重试。
响应在预算层处理限流归属后，下游只接收最终结果，不再次设置错误范围的冷却。

全局保护仍保留：例如 60 秒内至少 3 个不同出口都出现相同上游 5xx，暂停该上游 30 秒，
然后单次探测。该阈值是测试初值，应记录误触发情况后调整。

## 六、缓存与重启

- 上游暂不可用时，只能使用符合既有时效约定的缓存；不把过期天气或错误响应标成新数据。
  无合格缓存则返回明确的不可用状态。若以后允许过期数据展示，另行调整契约与页面时间标识。
- 单进程阶段保持内存调度和本地持久化；用同一写入任务原子保存节点、出口关联、
  最近各窗口用量、冷却时间和统计。分钟明细、小时与日时间桶保留各自必要窗口。
- 普通统计每 30 秒保存；429 冷却立即持久化。重启不能恢复出一份空白额度：
  对最近未落盘的区间保守预留，或先等待一个分钟窗口；缺失/损坏的长窗口账本恢复前
  暂停对应出口并检查，不能假定小时和日额度为零使用。
- 多进程/多实例之前，把预算、冷却和探测锁统一到 Redis 等共享存储，不能每个进程各算一份。

## 七、观测与验收

记录以下指标，按业务请求与后台探测分别统计，避免探活成功率掩盖页面失败：

- 已验证独立出口数、可用节点数、重复出口数、出口发生变化的次数。
- 业务最终成功率、首尝试成功率、每次成功的平均尝试数、P50/P95 延迟。
- 各出口分钟/小时/日用量，429 原因、冷却次数及恢复结果。
- 缓存命中率、列表刷新成功率、池耗尽次数、节点替换频率。

先在测试环境观测 24 小时，覆盖多个列表刷新周期和至少一次重启。以下为建议验收目标，
不是已达成结论：业务最终成功率至少 99%，平均尝试数不超过 1.2，代理传输 P95 不超过
5 秒，独立可用出口至少 5 个，无重试风暴和重启后额度清零。
样本不足时延长观察；至少记录 100 次自然发生或低速验证的业务回源，不为凑样本打满配额。

必须覆盖的自动化场景：

1. 同出口不同端口共享预算；不同出口的确定性分钟冷却互不误伤。
2. 请求到达上限之前完成预留，并发时不会超发；单批过大正确拆分。
3. 429 后只做最多一次允许的替代尝试，来源不明时仍执行共享冷却。
4. 空池、全部冷却、列表失败及时降级；没有隐式直连。
5. 同节点出口变化、出口探测失败、恢复旧状态时不会重复计算可用额度。
6. 重启恢复用量和冷却；检测与后台任务不会抢光前台名额。

## 八、实施顺序与代码范围

1. **出口识别与分组**：扩展 `weather_proxy_pool.py` 状态格式，加入实际出口观测、重复节点
   合并、候选状态与低水位补充；先证明“可用节点数”与“独立出口数”统计正确。
2. **预算与冷却归属**：重构 `providers/budget.py` 的项目总预算/出口预算，调整
   `weather_transport.py`、Open-Meteo Provider 和其他调用方处理 429 的位置。
   当前 `shared.retry_after` 会使整池暂停，不能只修改选代理函数而保留这个副作用。
3. **公平调度与有限重试**：预算有余量的出口间分散请求，统一两次尝试和总截止时间。
4. **测试环境验收**：备份状态格式与配置，部署可回退版本，完成故障注入和低速观察；
   验收通过后再决定是否推广到生产。保留现有开关和直连/原测试镜像恢复路径。

本阶段不新增独立代理管理服务，也不需要先部署 Redis；单实例轻量实现足够。
当免费出口的稳定性持续达不到验收目标时，再评估稳定的专用出网或上游服务方案，
不要通过无限增加候选数、重试数来掩盖失败。
