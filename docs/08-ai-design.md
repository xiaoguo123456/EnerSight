# 08 AI 分析设计 · AI Design

> EnerSight AI 新能源气象遥感分析平台 · 文档包 V1.0
>
> 产品名字里的 AI 具体怎么落地。对应 `packages/server/app/ai/`。


## 一、AI 在产品中的三个输出


AI 不是一个功能页面，是贯穿全产品的解释层。共三种输出：

| # | 输出 | 出现位置 | 长度 | 频率 |
| --- | --- | --- | --- | --- |
| 1 | 一句话结论 | 首页指数卡、地图 AI 提示条、站点详情 | 20–40 字 | 每小时 |
| 2 | 预警解释 | 预警卡的成因与影响说明 | 40–80 字 | 预警触发时 |
| 3 | 完整分析报告 | AI 分析报告页 | 结构化，约 400 字 | 每日一次 |


设计原则（承接 02 文档「AI解释优先」）：

```
不要输出：Cloud Cover 65%

要输出：  下午云量增加，可能影响发电效率
```

**AI 负责解释，不负责计算。** 所有数值由 07 文档的规则算出后作为输入喂给模型，
模型不做算术。这是准确性的底线 —— 让 LLM 算发电量必然出错。

## 二、模型选型


### 2.1 决定性因素是合规，不是能力

本产品是**面向境内公众的微信小程序**，这带来三个约束：

| 约束 | 说明 |
| --- | --- |
| 生成式 AI 服务备案 | 向境内公众提供生成式 AI 服务需完成备案/登记，境内模型厂商已具备资质 |
| 网络可达 | 境内服务器直连 Anthropic API 不通，需海外中转，延迟与稳定性都受影响 |
| 数据出境 | 用户位置与站点坐标属于需要评估的数据 |

> ⚠️ 以上为技术判断，**具体合规结论需法务确认**，不要以本文档为准。


### 2.2 建议

| 场景 | 模型 |
| --- | --- |
| 境内公开发布（V1 默认） | 境内已备案模型：DeepSeek / 通义千问 / 豆包 |
| 内部使用、海外版、评测基线 | Claude |

**无论选哪个，都必须做成可替换的 Provider 抽象**，见 2.4。


### 2.3 Claude 侧参数（若选用）

| 用途 | 模型 | 输入 $/1M | 输出 $/1M |
| --- | --- | --- | --- |
| 完整报告 | `claude-opus-5` | $5 | $25 |
| 完整报告（降本） | `claude-sonnet-5` | $2 | $10 |
| 一句话结论、预警解释 | `claude-haiku-4-5` | $1 | $5 |

调用要点（当前 API，与旧版本差异较大）：

- 思考用 `thinking: { type: "adaptive" }`，**不要用 `budget_tokens`**（已在 Opus 5 / Sonnet 5 上返回 400）
- 深度用 `output_config: { effort: "low" | "medium" | "high" | ... }`，本项目用 `low` 即可
- 结构化输出用 `output_config: { format: ... }`，**不是 `output_format`**（已废弃）
- Opus 5 / Sonnet 5 **不支持 assistant prefill**，格式控制走结构化输出


### 2.4 Provider 抽象

```python
# server/app/ai/provider.py
class AIProvider(Protocol):
    async def summarize(self, inp: SummaryInput) -> str: ...          # 一句话结论
    async def explain_alert(self, inp: AlertInput) -> str: ...        # 预警解释
    async def generate_report(self, inp: ReportInput) -> AIReport: ...  # 完整报告
```

切换模型只改一个实现文件，业务代码零改动。
上线前应对两家模型跑同一批样例做质量对比。

## 三、调用时机与缓存（成本关键）


### 3.1 绝不在用户请求时同步调 AI

用户打开首页时**不**触发 AI 调用。理由：

- 首屏要等模型返回，体感极差
- 同一区域上千用户会重复生成相同内容
- 成本随 DAU 线性增长，不可控


### 3.2 预生成 + 缓存

```
定时任务生成  →  写入缓存  →  用户请求直接读缓存
```

| 输出 | 触发 | 缓存键 | TTL |
| --- | --- | --- | --- |
| 一句话结论 | 每小时定时 | **0.25° 网格 + 站点类型** | 1 小时 |
| 预警解释 | 预警规则命中时 | 预警 ID | 随预警 |
| 完整报告 | 每日 08:00 定时 | 站点 ID + 日期 | 1 天 |

报告的生成时间与设计稿一致（站点3.png 显示「生成时间 08:00」）。


### 3.3 网格聚合是最大的省钱手段

一句话结论描述的是**区域气象条件**，不含站点私有数据，
因此同一 0.25° 网格内、同类型的站点可以共用一条结论。

```
1000 个站点  →  实际可能只落在 80–150 个网格

调用量下降近一个数量级
```

完整报告含站点装机、发电量等私有数据，**不能聚合**，按站点生成。

## 四、结构化输出


完整报告是强结构的（综合判断 / 三时段 / 风险 / 建议 / 摘要），
必须用结构化输出约束，不能让模型自由发挥后再正则解析。


### 4.1 Schema

```python
from pydantic import BaseModel, Field
from typing import Literal

class ReportPeriod(BaseModel):
    period: Literal["morning", "afternoon", "evening"]
    weather_summary: str                       # 「晴转多云」
    generation_impact: str                     # 「发电条件良好」
    level: Literal["good", "warning", "risk"]  # 时间轴节点配色

class AIReport(BaseModel):
    verdict_title: str          # 「今日适宜发电，下午存在轻度云层风险」
    verdict_detail: str         # 整体建议说明
    periods: list[ReportPeriod] = Field(min_length=3, max_length=3)
    risk_title: str
    risk_detail: str
    suggestions: list[str] = Field(min_length=2, max_length=3)
```

同一个 Pydantic 模型既约束模型输出，又参与 OpenAPI schema 生成 —— 
[06 契约](./06-api-contract.md) 的 `AIReportResponse` 由它派生，不必写两遍。

数据摘要（发电量 / 等效小时 / CO₂ / 收益）**不进 schema** —— 那是算出来的，
由服务端直接填充，不经过模型。


### 4.2 调用（Claude 侧示例）

```python
import anthropic

client = anthropic.Anthropic()

response = client.messages.parse(
    model="claude-opus-5",
    max_tokens=4000,
    system=[
        {"type": "text", "text": SYSTEM_PROMPT,
         "cache_control": {"type": "ephemeral"}},
    ],
    messages=[{"role": "user", "content": build_report_input(station, metrics)}],
    output_format=AIReport,
)

# 解析失败时 parsed_output 为 None，必须判空后降级
report = response.parsed_output
if report is None:
    return fallback_report(station, metrics)
```

## 五、Prompt 设计


### 5.1 输入构造

模型只接收**算好的结论**，不接收原始数据流：

```
站点：苏州光伏站，光伏，装机 500 kW，江苏省苏州市吴中区

今日环境指数：81 分（良好）
  辐射 83 分 / 云量 65 分 / 温度 86 分 / 风速 100 分

分时段气象：
  上午 06-12  晴转多云  平均辐射 520 W/m²  云量 20%
  下午 12-18  云量增加  平均辐射 380 W/m²  云量 55%
  晚间 18-24  多云转晴  —

预警：14:30 后云量增加，预计辐射下降 20%（轻度）

估算：日发电 2,400 kWh，等效 4.8 h
```


### 5.2 System Prompt 要点

```
你是新能源电站的运维分析助手，为光伏与风电站点生成每日分析。

规则：
1. 只解释给定数据，不做任何算术，不引入未提供的数字
2. 面向电站运维人员，用运营语言而非气象术语
3. 每条运营建议必须是可执行动作，不写「注意天气」这类空话
4. 无风险时如实说明，不要为了填满结构编造风险
5. 中文输出，简洁，不使用 emoji 与 markdown 标记
```

第 4 条很重要：结构化输出会诱导模型把每个字段都填满，
必须显式允许「今日无明显风险」这类输出。


### 5.3 Prompt Caching

固定前缀（system prompt + 输出规范）缓存，变动部分（站点数据）放后面。

```
tools  →  system  →  messages
         ↑ 缓存断点放这里
```

要点：

- 前缀里**不能出现时间戳**、请求 ID 等每次变化的内容，否则缓存永远不命中
- 最多 4 个缓存断点
- 用 `usage.cache_read_input_tokens` 验证是否真的命中，恒为 0 说明前缀被污染了

## 六、降级策略


**AI 挂掉不能让页面白屏。** 每个 AI 输出都要有规则兜底。

| 场景 | 降级 |
| --- | --- |
| 调用超时（> 10s） | 用规则模板 |
| 结构化解析失败 | 用规则模板 |
| 内容审核拦截 | 用规则模板 |
| 服务不可用 | 用上一次缓存结果，标注生成时间 |


规则模板示例（一句话结论）：

```
指数 ≥ 85   →  今日发电条件优秀
70 – 84     →  今日适宜发电
55 – 69     →  今日发电条件一般
< 55        →  今日发电条件较差，建议关注

若存在预警，追加：{时刻}后{风险类型}，注意{影响}
```

规则模板的输入与 AI 完全一致（都来自 07 的指标），
所以兜底文案不会与页面数据矛盾。


降级不向用户暴露技术细节，不显示「AI 服务异常」。

## 七、成本估算


按 **100 个站点、30 个有效网格**测算（Claude 侧，人民币按 7.1 折算）：

| 输出 | 调用量/天 | 模型 | 输入 | 输出 | 日成本 |
| --- | --- | --- | --- | --- | --- |
| 一句话结论 | 720 | Haiku 4.5 | 1.5K | 120 | ≈ $1.5 |
| 预警解释 | 20 | Haiku 4.5 | 1.5K | 200 | ≈ $0.05 |
| 完整报告 | 100 | Sonnet 5 | 3K | 1.5K | ≈ $2.1 |
| **合计** | | | | | **≈ $3.7/天 ≈ ¥790/月** |

报告改用 Opus 5：合计约 $6.9/天 ≈ ¥1,470/月。

启用 prompt caching 后，输入部分还可再降 30–50%。


成本随站点数增长的特征：

```
一句话结论  →  随网格数增长，站点翻倍成本远不到翻倍
完整报告    →  随站点数线性增长，是主要成本项
```

若站点规模上万，报告应改为**按需生成 + 长缓存**（用户打开才生成，缓存 1 天），
或降级为规则模板 + AI 仅生成综合判断段。

## 八、质量保障


| 项 | 做法 |
| --- | --- |
| 评测集 | 构造 30 组典型气象场景（晴天 / 阴天 / 强风 / 高温 / 有预警 / 无预警），人工标注期望结论 |
| 回归 | Prompt 或模型变更后跑全量评测集，人工抽检 |
| 数值一致性 | 自动校验：模型输出中出现的数字必须全部来自输入，不允许新增 |
| 空话检测 | 建议条目中「注意」「关注」占比过高时告警 |
| 线上抽样 | 每日抽 5% 输出留档，供人工复核 |


数值一致性校验是最重要的一条：
正则提取输出中的所有数字，逐个比对是否在输入里出现过，
不匹配即判定为幻觉，走降级模板。
